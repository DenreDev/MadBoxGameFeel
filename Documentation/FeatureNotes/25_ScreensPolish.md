# FEATURE: Boot, start and game over screens

## 1. Summary
A boot cover (gradient, "BEE SLAYER" title, bouncing loading dots) hides the loading from the very first frame, then zooms out and fades. The start screen drops its title in, pops a chunky "TAP TO START" button and fades in a controls hint. On tap the button punches and the title flies away. Game over plays a short sequence: dim, "GAME OVER" slam, round stats (wave reached, kills), then a "TRY AGAIN" button. Buttons squash under the finger.

## 2. Why / issue fixed
- **Why (from the human):** to improve the overall juice of the game.
- **Issue fixed (deduced from that statement and the audit):** the first frames showed an empty purple sky with a "TAP TO START" that did nothing until every service and Addressable preload was done. The start and game over screens looked like default prototype UI: default font, flat grey box, plain white text, stock Unity button. The game had to feel high quality from the first frame to the last.

> The issue wording is deduced, to be confirmed by the human.

## 3. Bottleneck
Not given by the human. Deduced from the work: checking UI timings in the shared, unfocused editor. The capture probe counted frames at a fixed capture rate while the UI runs on real time, so early captures showed screens "not there yet". The probe had to time the UI phases in real milliseconds.

## 5. Files changed
- `BootCoverView.cs`: new. Shown from frame 1, fades out after `OnAllServicesInitialized`, then disables itself.
- `StartScreenView.cs`: intro (title drop with overshoot, prompt pop, hint fade) and exit (prompt punch, title fly-up, fade). Hidden until services answer.
- `GameOverOverlayView.cs`: timed sequence, round stats counted from `OnWaveStarted` and `OnEnemyKilled`, button interactable only once visible.
- `ButtonPressFeedback.cs`: new. Damped spring squash on pointer down, bouncy release.
- `UI/View/Local/Common/`: generated `RoundedRect` (9-sliced), `Circle`, `SoftGlow`, `BootGradient` sprites and `UITitle` / `UILabel` TMP materials (thick outline + drop shadow).
- `MainScene.unity`: new `UI/BootCover`, start screen `Title`, `TopShade`, `Hint`, restyled prompt, game over `Stats`, `TitleGlow`, `RestartGroup`.

No gameplay code changed. The views only listen to events that already existed.

## 6. Technical flow
1. Frame 1: `BootCover` is the last child of the UI canvas, opaque and blocking taps. The start screen behind it keeps its title and prompt hidden.
2. Services finish initializing: the cover waits for its minimum display time, then fades with a title zoom. In the same moment the start screen starts its intro: title drops after 0.2 s, prompt pops 0.45 s later, hint fades in last.
3. Tap: `GameFlowService.StartGame()` (unchanged). The start screen sees `Playing` and plays its exit.
4. Hero dies: the flow goes to `GameOver`. The overlay waits 0.6 s for the death, dims, slams the title, raises the stats, pops the button. The button becomes interactable when the pop ends.
5. Try again: `Restart()` goes back to `Start`, the overlay resets its stats, the start screen replays its intro. The boot cover stays off: services are not reloaded.

All UI animation runs on unscaled time so hit-stop freeze frames never stall it.

## 7. Tuning values
Boot cover:
- `minDisplayDuration` = `0.5`: seconds the cover stays at least
- `fadeDuration` = `0.45`, `titleExitScale` = `1.25`: exit fade and title zoom
- `dotBounceHeight` = `18`, `dotBounceSpeed` = `1.6`: loading dots

Start screen:
- `titleDelay` = `0.2`, `titleDropDuration` = `0.55`, `titleDropHeight` = `420`: title entrance
- `promptDelay` = `0.45`, `promptPopDuration` = `0.4`: prompt entrance
- `titleSwayAngle` = `2.5`: idle sway
- `tapPunchScale` = `1.3`, `titleExitRise` = `260`, `fadeDuration` = `0.3`: exit

Game over:
- `startDelay` = `0.6`: lets the death play before the screen shows
- `dimDuration` = `0.5`, `titleSlamDuration` = `0.3`, `titleStartScale` = `2.8`: dim and slam
- `statsDelay` = `0.35`, `statsRiseDistance` = `40`: stats
- `buttonDelay` = `0.4`, `buttonPopDuration` = `0.35`: button pop

Button press:
- `pressedScale` = `0.9`, `stiffness` = `600`, `damping` = `0.35`: squash and wobble

## 8. Addressables
- **Used?** No, on purpose.
- **Why not:** the boot cover is what the player looks at while Addressables load, so its sprites must be direct references. The start and game over sprites are scene UI that is always on screen at launch or always one state away. They are tiny (largest 128x128) and loading them remotely would only add a failure case.
- **Remote readiness:** if the screens became heavier content (animated logo, skins), the start and game over art could move to a `UI` group and be preloaded with the other feedback assets. The boot cover would stay local.

## 9. Generated assets
- **Used?** Yes, all generated by a throwaway editor builder (deleted after use), included in the 14 min.
- `RoundedRect.png` (128x128, 9-slice border 62): button lips, faces, shine and stats panel.
- `Circle.png` (64x64): loading dots.
- `SoftGlow.png` (128x128 radial): title halos and the top shade.
- `BootGradient.png` (4x256): violet to pink boot background, matching the sky palette.
- `UITitle.mat`, `UILabel.mat`: LiberationSans SDF with a dark purple outline and drop shadow.
- **Replacement cost:** low. Swap the sprite or material reference, no code change. A real cartoon font is the obvious next replacement.

## 10. Edge cases and limits
- Fast load: the cover still shows 0.5 s, so it never flashes.
- Tap before services are ready: the cover blocks raycasts, and `StartScreenView` already ignores a tap without a game flow.
- Player still swiping at death: the restart button ignores taps until it has popped in.
- Restart: stats reset on `Start`, the intro replays, the cover does not come back.
- Not built: a cartoon display font (needs a download), UI sounds, a "GO!" moment, slow-motion death, HUD restyle of the wave badge and combo counter.
- The title "BEE SLAYER" is a placeholder.

## 11. Base project observations
- The console logs "Particle Velocity curves must all be in the same mode" errors.
- Nothing hid the loading: `ServicesLocator` initializes asynchronously and the UI was visible before it was usable.

## 12. Likely review questions
- **Why not load the boot cover with Addressables?** It is the screen shown while Addressables load. It must be available on frame 1.
- **How does the cover know loading is done?** It subscribes to `ServicesLocator.OnAllServicesInitialized`, which already fires once every service, preloads included, is ready.
- **Who counts kills for the game over stats?** The overlay view itself, from `OnEnemyKilled` and `OnWaveStarted`. No gameplay class tracks numbers for the UI.
- **Why does the game over view drive a wrapper and the button a child scale?** The pop-in and the press squash are two scales on two transforms, so they never fight.
- **Why unscaled time?** Hit stop freezes `Time.timeScale`; UI must keep animating through it.

## 13. 30-second explanation
The first thing the player saw was an empty sky and a start prompt that did not respond, and the start and game over screens looked like default prototype UI. A boot cover now hides the loading and hands over to an animated start screen, and game over plays a short dim, slam, stats, button sequence. Everything is view code listening to existing events, tuned in the inspector, on unscaled time. The main trade-off: the screen sprites are direct references, because the cover must exist before Addressables are ready.
